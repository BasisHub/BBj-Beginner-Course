## Summary

Phase 3 modernizes four existing content sections (Getting Started, Object-Oriented, File I/O, Web Development) by making content text-first, restructuring OOP into subpages, reframing File I/O as legacy context, and normalizing tone to a professional peer voice. This is primarily a content editing and restructuring phase, not a technology integration phase.

The existing codebase is Docusaurus 3.9.2 with all necessary infrastructure already in place. The DWC tutorial provides a proven reference pattern for multi-page chapters (numbered `.md` files within numbered folders, `index.md` as category landing page). The main technical decisions involve: (1) how to wrap videos in collapsible containers, (2) how to split the OOP monolith into subpages, and (3) what degree of rewriting to apply to Getting Started prose.

**Primary recommendation:** Follow DWC tutorial subpage conventions exactly. Use `<details>`/`<summary>` HTML elements for collapsible video wrappers. Rewrite in passes: structure first (split/move files), then content (tone, text-first).

## Architecture Patterns

### Recommended File Structure for OOP Chapter Split

The OOP chapter (currently `docs/03-object-oriented/index.md`) must be split into subpages. Follow the DWC tutorial convention:

```
docs/03-object-oriented/
├── index.md              # Chapter landing page (overview, what this chapter covers)
├── 01-writing-classes.md # BBj class syntax, inheritance, interfaces, constructors
├── 02-using-java.md      # HashMap, Iterator, Java interop from BBj
└── 03-bbjapi-model.md    # BBjAPI() orientation: what it is, main object families
```

This mirrors the DWC tutorial pattern seen in:
```
docs/01-gui-to-bui-to-dwc/
├── index.md
├── 01-registering-launching.md
├── 02-hello-world.md
└── 03-gui-to-bui-to-dwc.md
```

**Key conventions (verified from DWC tutorial):**
- Subpage files use `sidebar_position` frontmatter (1, 2, 3...) for ordering
- The `index.md` in each folder acts as the category landing page automatically
- No `_category_.json` files are needed (neither tutorial uses them)
- The Docusaurus number prefix stripping handles URLs: `01-writing-classes.md` becomes `/object-oriented/writing-classes`
- The existing `sidebars.ts` entry `{type: 'autogenerated', dirName: '03-object-oriented'}` already handles subpages -- Docusaurus autogeneration picks up all `.md` files in the directory

### Pattern 1: Collapsible Video Wrapper

**What:** Wrap YouTube iframe embeds in `<details>`/`<summary>` so videos are supplementary, not primary.

**When to use:** Every YouTube video embed across all four sections.

**Example:**
```markdown
<details>
<summary>Watch the video: A First Hello World</summary>

<iframe width="560" height="315" src="https://www.youtube.com/embed/fF9LaVXJGuA" title="A First Hello World" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture" allowfullscreen></iframe>

</details>
```

Source: [Docusaurus Markdown Features](https://docusaurus.io/docs/markdown-features) -- confirms `<details>` is styled beautifully by Docusaurus.

**Important MDX notes:**
- Keep `<summary>` content on a single line (MDX creates extra `<p>` tags for line breaks)
- Blank line required between `<summary>` closing tag and content inside `<details>`
- Blank line required before closing `</details>` tag
- This works in `.md` files (which Docusaurus processes as MDX by default in v3)

### Pattern 2: Text-First Content with Video Supplement

**What:** Every section that currently relies on a video for instruction must have complete text-based content that stands alone. The video becomes a "Watch the video" collapsible after the text.

**When to use:** All 9 YouTube video embeds across Getting Started (5), OOP (3), and Web Development (1).

**Structure per section:**
```markdown
## Section Title

[Complete text-based instruction, code examples, explanation]

<details>
<summary>Watch the video: Section Title</summary>

<iframe ...></iframe>

</details>
```

### Pattern 3: Professional Peer Tone

**What:** Replace casual/instructional prompts with direct, peer-level statements.

**When to use:** Throughout all four sections.

**Transform rules:**
| Current Pattern | Replace With |
|----------------|--------------|
| "Play with it" | "Experiment with variations" or structured exercise |
| "Can you enhance it?" | "Exercise: Add a button to clear both input fields" |
| "Watch this video" | (Move video to collapsible) |
| "Now it's time to learn" | Direct statement of what the section covers |
| "Let's start with" | Direct statement |
| "You will need to have learned about" | "This material assumes familiarity with" |
| "Check with your manager" | Remove or rewrite as resource pointer |

### Anti-Patterns to Avoid

- **Monolith splitting without content continuity:** When splitting OOP into subpages, ensure the `index.md` landing page provides clear navigation context so readers know the three-subpage structure.
- **Losing existing code examples during rewrite:** The Getting Started calculator example and the OOP dialog examples are solid -- preserve them, just normalize tone around them.
- **Over-writing File I/O:** The File I/O chapter is already comprehensive and well-structured. The modernization is mostly the intro framing and chapter title -- don't rewrite the body content.
- **Breaking internal links:** When moving comparison tables from Getting Started to Introduction, verify no other pages link to those sections.

## Common Pitfalls

### Pitfall 1: MDX Parsing Errors with `<details>` in `.md` Files

**What goes wrong:** Curly braces `{}` or JSX-like syntax inside `<details>` blocks can cause MDX compilation errors.
**Why it happens:** Docusaurus 3 processes all `.md` files as MDX by default, so HTML embedded in markdown is parsed as JSX.
**How to avoid:** Keep video iframes straightforward (no JavaScript or curly braces inside). The YouTube embed code used in the project is plain HTML attributes and works fine.
**Warning signs:** Build errors mentioning "unexpected token" or "JSX" in markdown files.

### Pitfall 2: Broken Links After Content Reorganization

**What goes wrong:** Moving the "BBj for Java/.NET Developers" comparison tables from Getting Started to Introduction may break internal references.
**Why it happens:** Other pages may link to anchors like `/getting-started#bbj-for-javanet-developers`.
**How to avoid:** Before moving content, grep for all internal links to the affected section anchors. After moving, update any references.
**Warning signs:** `npm run build` will catch broken links (configured as `onBrokenLinks: 'throw'`).

### Pitfall 3: OOP Subpage Sidebar Ordering

**What goes wrong:** Subpages appear in wrong order in sidebar.
**Why it happens:** Without `sidebar_position` frontmatter, Docusaurus uses alphabetical file ordering.
**How to avoid:** Every new subpage `.md` file must include `sidebar_position` in frontmatter. The number prefix (01-, 02-, 03-) also helps but frontmatter is the authoritative ordering.
**Warning signs:** Subpages appearing in wrong order during `npm start`.

### Pitfall 4: Getting Started Becomes Too Thin

**What goes wrong:** Over-aggressive rewriting removes content that readers actually need, especially the calculator example and GUI basics.
**Why it happens:** The peer-tone directive could be misinterpreted as "remove all tutorial content."
**How to avoid:** The tone rewrite should change voice, not substance. Code examples, syntax explanations, and step-by-step progressions stay. What changes: "Play with it" becomes structured exercises, "Watch the video" becomes collapsible supplements, casual phrasing becomes direct.
**Warning signs:** Sections that lose their code examples or become mere link collections.

### Pitfall 5: File I/O Renaming Signals Deprecation

**What goes wrong:** A chapter title like "Legacy File I/O" makes readers think the content is irrelevant.
**Why it happens:** The word "legacy" can imply "don't learn this."
**How to avoid:** Frame it as context, not deprecation. Titles like "Record-Oriented Files" or "File I/O and Record Access" with a subtitle note work better. The intro paragraph already frames the modern path.
**Warning signs:** A title that would discourage a developer from reading the chapter when they need to understand the legacy codebase they just inherited.

    key! = iter!.next()

### BBjAPI Object Model Orientation

```bbj
rem BBjAPI() is the entry point for all BBj built-in objects
api! = BBjAPI()

rem GUI: Open a SysGui context and create windows
sysgui! = api!.openSysGui("X0")
wnd! = sysgui!.addWindow(10, 10, 400, 300, "My Window")

rem Collections: Create vectors (dynamic arrays)
vect! = api!.makeVector()
vect!.addItem("item1")

rem Namespaces: Share data between programs
ns! = api!.getNamespace("myApp", "shared", 1)
ns!.setValue("key", "value")
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| BBj classes interpreted at runtime | BBj classes cross-compiled to Java bytecode | BBj 21.00 | Better performance, reflection support |
