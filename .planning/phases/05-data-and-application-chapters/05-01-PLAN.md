| Verb/Function | Syntax | Purpose |
|---------------|--------|---------|
| SQLOPEN | `SQLOPEN(chan)"dbname"` | Open database connection |
| SQLPREP | `SQLPREP(chan)"sql$"` | Prepare SQL statement |
| SQLTMPL | `DIM rec$:SQLTMPL(chan)` | Get result template for field access |
| SQLEXEC | `SQLEXEC(chan)args` | Execute prepared statement |
| SQLFETCH | `rec$=SQLFETCH(chan,END=done)` | Fetch next result row |
| SQLCLOSE | `SQLCLOSE(chan)` | Close connection |
| SQLERR | `SQLERR(chan)` | Get last SQL error text |

**File 3: `docs/08-database-sql/02-queries.md`**

Frontmatter: `sidebar_position: 2`, `title: "Queries and Results"`

Content sections:
1. **Opening (2-3 sentences):** Once connected, you prepare SQL statements with SQLPREP, execute them with SQLEXEC, and fetch results with SQLFETCH. The key insight is SQLTMPL -- it returns a template string that lets you access result columns by name using BBj's dot notation on dimensioned strings.

2. **The Query Lifecycle:** Walk through the complete sequence with a SELECT example against CUSTOMER table. Use the verified pattern from RESEARCH.md:
   ```bbj
   SQLOPEN(1)"ChileCompany"
   SQLPREP(1)"SELECT CUST_NUM, FIRST_NAME, LAST_NAME, COMPANY FROM CUSTOMER WHERE LAST_NAME LIKE ?"
   DIM rec$:SQLTMPL(1)
   SQLEXEC(1)"S%"
   WHILE 1
       rec$ = SQLFETCH(1, END=done)
       PRINT rec.CUST_NUM$, " ", rec.FIRST_NAME$, " ", rec.LAST_NAME$
   WEND
   done:
   SQLCLOSE(1)
   ```
   Explain each verb step by step. Emphasize: `DIM rec$:SQLTMPL(1)` must come AFTER SQLPREP and BEFORE SQLFETCH. The template defines available fields.

3. **Field Access with SQLTMPL:** Explain the template string concept. SQLTMPL returns something like `CUST_NUM:C(6),FIRST_NAME:C(20),LAST_NAME:C(30)`. After `DIM rec$:SQLTMPL(1)`, you access character fields with `$` suffix (`rec.FIRST_NAME$`) and numeric fields without suffix (`rec.COST`). Show a gotcha box: forgetting the `$` suffix on character fields causes type mismatch errors.

4. **Parameterized Queries (SQLPREP + SQLEXEC):** Explain `?` placeholders in SQLPREP. SQLEXEC passes values positionally as comma-separated arguments. Show both a single-parameter and multi-parameter example.

5. **Why Prepared Statements:** Two benefits: (1) SQL injection prevention -- user input is never concatenated into the SQL string. Show a BAD example (string concatenation) vs GOOD example (parameterized). (2) Performance -- the database can reuse the query plan when parameters change.

6. **INSERT, UPDATE, DELETE:** Show INSERT example from RESEARCH.md (INSERT INTO CUSTOMER with 4 parameters). Show an UPDATE example. Note these do not return results, so SQLFETCH is not needed.

7. **Handling End of Results:** `END=lineref` on SQLFETCH handles the normal end-of-results condition (ERROR 2 internally). Use `END=` for this, reserving `ERR=` for actual SQL errors. Show both approaches: `END=done` label pattern and `ERR=` with error number check.

Legacy callout: "Reading Legacy Code: String-Based SQL Without Templates"
- Early BBj code may build SQL strings dynamically using string concatenation
- No SQLPREP or parameterization -- SQL injection risk
- Fixed-width `MID()` parsing of results instead of SQLTMPL dot notation
