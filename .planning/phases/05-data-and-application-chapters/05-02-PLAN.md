**File 3: `docs/09-java-interop/02-advanced.md`**

Frontmatter: `sidebar_position: 2`, `title: "Advanced Java Patterns"`

Content sections:
1. **Opening (2-3 sentences):** Beyond basic usage, BBj can implement Java interfaces, handle Java exceptions gracefully, and access external libraries through classpath configuration. These patterns unlock the full power of the Java ecosystem.

2. **Implementing Java Interfaces:** Absorb and expand the Comparator example from the existing OOP page. Show the full pattern:
   - BBj `class public ... implements InterfaceName`
   - Method signatures must match the interface
   - The BBj class can then be passed to any Java API expecting that interface
   - Show Comparator with Collections.sort() example

3. **Generics: Raw Types Only:** BBj does not support Java generics syntax. Always use raw types: `new HashMap()`, never `new HashMap<String, String>()`. BBj resolves types at runtime. This means no compile-time type safety for Java generic types. Show a gotcha: angle brackets cause syntax errors in BBj.

4. **Handling Java Exceptions (Error 252):** When a Java method throws, BBj traps it as error 252. Show the ERR= pattern (NOT try/catch -- BBj does not have try/catch):
   ```bbj
   use java.util.HashMap
   map! = new HashMap()
   value! = map!.get("key")  ; rem returns null, no exception
   rem But for methods that DO throw:
   seterr java_err
   rem ... risky Java call ...
   java_err:
   ex! = BBjAPI().getLastJavaException()
   print "Java exception: ", ex!.getMessage()
   ```
   Cross-link to [error handling chapter](/error-handling/patterns) for the full error 252 pattern.

5. **Classpath Configuration:** When you need an external JAR beyond what BBj bundles:
   - Enterprise Manager -> Java Settings -> Classpath
   - Add the JAR path to the classpath
   - Restart BBjServices for the change to take effect
   - Then `use` the classes from that JAR in your BBj code
   - Brief, practical walkthrough (not a full Enterprise Manager tutorial)

6. **Limitations Summary:** Consolidate from the existing OOP page:
   - No generics syntax (raw types only)
   - Runtime type resolution (no compile-time type checking for Java calls)
   - Java exceptions become error 252
   - Object identity differences across BBj/Java boundary

Legacy callout: "Reading Legacy Code: Pre-Use Import Patterns"
- Before `use` was added, all Java classes required fully qualified names
- `obj! = new java.util.HashMap()` on every reference
- Some code uses `ADDR()` and `CALL` for Java method invocation in very old programs
