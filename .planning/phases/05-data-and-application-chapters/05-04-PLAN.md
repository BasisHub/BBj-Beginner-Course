**File 2: `docs/11-debugging/01-console.md`**

Frontmatter: `sidebar_position: 1`, `title: "Console Debugging"`

Content sections:
1. **Opening (2-3 sentences):** The BBj console is your primary debugging tool. When you break into a running program, you get an interactive prompt where you can step through code, inspect variables, and evaluate expressions -- all while the program is paused.

2. **Breaking into the Console:** Explain three ways to pause a running program:
   - **Ctrl-C / Ctrl-Break:** Keyboard interrupt while program is running. Pauses at the current line.
   - **ESCAPE verb:** Add `ESCAPE` to your code to create a programmatic breakpoint. When execution reaches it, the program pauses and drops to the console.
   - **Error occurrence:** When an unhandled error occurs (no SETERR or ERR= trap), BBj drops to the console at the error line.

   When you break in, BBj shows the current line number and waits for your input.

3. **Dot-Stepping:** The core debugging workflow. Present the command reference table:

| Command | Action |
|---------|--------|
| `.` + Enter | Execute one line (single step into) |
| `..` + Enter | Execute one line, stepping over subroutine/method calls |
| `. n` | Execute next n lines |
| `.. n` | Step over n lines |

   Explain: After each step, BBj shows the next line to be executed. This lets you trace the exact flow of your program. `.` steps INTO method calls (you see each line inside the method), while `..` steps OVER them (the method executes and you see the result).

4. **Variable Inspection and Modification:** At the console prompt, you have full access to program state:
   - `? variableName` or `PRINT variableName` -- display a variable's value
   - `? obj!.method()` -- call a method and display the result
   - `variableName = newValue` -- change a variable's value at runtime
   - `? expression` -- evaluate any BBj expression

   Show practical examples:
   ```
   > ? name$
   Alice
   > ? count
   42
   > ? items!.size()
   3
   > count = 100
   > ? count
   100
   ```

   This is a live REPL -- you can test fixes before modifying your source code.

5. **Searching Program Text:** `\searchstring` searches the loaded program for text. Useful when you break in and need to find a specific label, variable, or method. The search wraps around from the current position.

6. **Navigating Methods:** `methodret` at the console exits the current method and returns to the caller. Useful when you have stepped into a method you don't need to debug.

7. **Diagnosing BEM Errors:** When BBj reports an error, it shows three pieces of information:
   - **Error number:** The BBj error code (e.g., 11 = end of file, 17 = invalid file, 252 = Java exception)
   - **Line number:** Where in your program the error occurred
   - **Error message:** A human-readable description

   Show how to use this information:
   ```
   !ERROR=11 Line 45
   ```
   This means error 11 (end of file) at line 45. To diagnose:
   1. Check line 45 of your program to see what operation was attempted
   2. Look up error 11 in the error codes reference
   3. The error handling chapter covers error code lookup and common error numbers -- cross-link to [Error Handling](/error-handling/seterr-and-err) for the full list

   Do NOT reproduce the error codes table here -- it already exists in the error handling chapter.

8. **Console Access Control:** Brief note (2-3 sentences). In production, console access may be disabled via Enterprise Manager ("Disallow Console" setting) or `STBL("!CONPASS")` for password protection. During development, ensure console access is enabled for debugging.

**File 3: `docs/11-debugging/02-tracing.md`**

Frontmatter: `sidebar_position: 2`, `title: "Tracing and Logging"`

Content sections:
1. **Opening (2-3 sentences):** When interactive debugging is not practical -- the bug is intermittent, happens in production, or involves complex timing -- you need to record what the program does. BBj provides DUMP for snapshots and SETTRACE for execution logging, plus several options for adding your own log output.

2. **DUMP: Variable Snapshot:** The DUMP verb writes all current variables to a destination. Two forms:
   - `DUMP` -- prints all variables to the console (useful when already at the console)
   - `DUMP(chan)` -- writes all variables to an open file channel

   Show the file-based example:
   ```bbj
   name$ = "Alice"
   count = 42
   items! = BBjAPI().makeVector()
   items!.addItem("one")
   items!.addItem("two")
   open(7, mode="O_CREATE,O_TRUNC")"/tmp/debug_dump.txt"
   dump(7)
   close(7)
   print "Variables dumped to /tmp/debug_dump.txt"
   ```

   Explain: DUMP writes every variable in scope -- strings, numbers, and object references. For large programs this can be verbose, but it is invaluable for post-mortem debugging when you cannot reproduce the issue interactively.

   **Filtered DUMP:** `DUMP(0, MODE="vars,level="+str(tcb(13)))` dumps only variables at the current scope level. Useful inside methods to avoid seeing all global variables.

3. **SETTRACE / ENDTRACE: Execution Trace:** SETTRACE records every line executed to a file channel. ENDTRACE stops recording. This produces a complete execution trace showing the exact path through your program.

   Show example:
   ```bbj
   open(8, mode="O_CREATE,O_TRUNC")"/tmp/debug_trace.txt"
   settrace(8)
   for i = 1 to 3
       print "Loop iteration: ", i
   next i
   endtrace
   close(8)
   print "Trace written to /tmp/debug_trace.txt"
   ```

   Explain: The trace file shows each line number and statement as it executes. For loops, you see each iteration. For method calls, you see entry and exit. This is especially useful for understanding flow through complex conditional logic.

   **Gotcha box (:::caution):** SETTRACE generates large output files quickly. Trace only the section of code you are investigating, and use ENDTRACE to stop as soon as possible. A trace of even a simple loop produces one line per iteration.

4. **Logging Techniques:** When you need persistent debug output without the full weight of SETTRACE, add logging to your code. Three approaches:

   **Logging methods table:**

| Method | Output Destination | When to Use |
|--------|-------------------|-------------|
| `System.out.println(var$)` | BBj debug log (server-side) | Server-side logging, viewable in Enterprise Manager |
| `sysGui!.executeScript("console.log('msg')")` | Browser console | BUI/DWC debugging only |
| `MSGBOX(var$)` | Dialog popup | Quick visual check (blocks execution) |
| `PRINT var$` | Console / terminal | Simple output during development |

   Show System.out.println example:
   ```bbj
   use java.lang.System
   System.out.println("Debug: entering processOrder, id=" + str(orderId))
   ```

   Explain: `System.out.println()` writes to the BBj debug log, which persists and can be viewed in Enterprise Manager's log viewer. This is the closest BBj equivalent to a logging framework. For quick-and-dirty checks, `PRINT` works but output goes to the console/terminal and is lost when the program ends.

5. **IDE Debugger (Brief):** In 3-4 sentences, mention that the BBj IDE (BDT - BBj Development Tools for Eclipse, and the newer VS Code extension) includes a visual debugger with breakpoints, variable watches, and step controls. These wrap the same underlying console debugging capabilities in a GUI. For teams using an IDE workflow, the visual debugger is a convenient option. This tutorial focuses on console debugging because it works everywhere and does not require IDE setup.

- Older code may use `SETTRACE` alone for interactive tracing while watching the console
- The file-based form `SETTRACE(chan)` is more practical for capturing output
