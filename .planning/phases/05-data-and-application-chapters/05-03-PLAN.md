2. **Opening (2-3 sentences):** BBj programs respond to user actions -- button clicks, text changes, window closes -- through event callbacks. | ON_BUTTON_PUSH | `ctrl!.ON_BUTTON_PUSH` | Button click event constant |
| ON_CLOSE | `window!.ON_CLOSE` | Window close event constant |
| ON_EDIT_MODIFY | `ctrl!.ON_EDIT_MODIFY` | Text change event constant |

**File 2: `docs/10-event-handling/01-setcallback.md`**

Frontmatter: `sidebar_position: 1`, `title: "setCallback and process_events"`

Content sections:
1. **Opening (2-3 sentences):** The `setCallback` method registers a callback on a control for a specific event type. When that event fires, BBj calls your handler. Combined with `process_events`, this is how all modern BBj GUI programs work.

2. **SYSGUI and Window Basics (brief):** In 3-4 sentences, explain that GUI programs open a SYSGUI device with `BBjAPI().openSysGui("X0")`, then create windows and controls through it. `addWindow` creates a BBjWindow, and window methods like `addButton` and `addInputE` create controls. This is setup plumbing -- the interesting part is how you respond to events on those controls. Show minimal setup:
   ```bbj
   sysgui! = BBjAPI().openSysGui("X0")
   window! = sysgui!.addWindow(10, 10, 400, 200, "My App", $00100083$)
   button! = window!.addButton(201, 50, 50, 100, 30, "Click Me")
   ```

3. **Label-Based Callbacks:** Show the simpler form first. `ctrl!.setCallback(ctrl!.ON_BUTTON_PUSH, "labelName")` registers a label. When the event fires, BBj GOSUBs to that label. You MUST `return` from the label. To access the event object, call `BBjAPI().getSysGui().getLastEvent()`. Show the full label-based example:
   ```bbj
   sysgui! = BBjAPI().openSysGui("X0")
   window! = sysgui!.addWindow(10, 10, 400, 200, "Simple App", $00100083$)
   button! = window!.addButton(201, 50, 50, 100, 30, "Click Me")
   button!.setCallback(button!.ON_BUTTON_PUSH, "onButtonPush")
   window!.setCallback(window!.ON_CLOSE, "onClose")
   process_events
   onButtonPush:
       event! = BBjAPI().getSysGui().getLastEvent()
       a = msgbox("Button clicked!", 0, "Event")
   return
   onClose:
       release
   return
   ```
   Explain each part: setCallback registers the label, process_events starts the loop, the label handler executes and returns.

4. **Method-Based Callbacks (Recommended):** Show the OO form: `ctrl!.setCallback(ctrl!.ON_BUTTON_PUSH, #this!, "methodName")`. The callback method receives the event object as a parameter -- no need for getLastEvent(). The method parameter type MUST match the event type (e.g., `BBjButtonPushEvent` for ON_BUTTON_PUSH). Show the full class-based example:
   ```bbj
   class public MyApp
       field private BBjWindow window!
       field private BBjButton button!
       field private BBjInputE input!

       method public void run()
           sysgui! = BBjAPI().openSysGui("X0")
           #window! = sysgui!.addWindow(10, 10, 400, 200, "My App", $00100083$)
           #button! = #window!.addButton(201, 50, 50, 100, 30, "Click Me")
           #input! = #window!.addInputE(202, 50, 100, 200, 30, "")
           #button!.setCallback(#button!.ON_BUTTON_PUSH, #this!, "onButtonPush")
           #input!.setCallback(#input!.ON_EDIT_MODIFY, #this!, "onTextChange")
           #window!.setCallback(#window!.ON_CLOSE, #this!, "onClose")
           process_events
       methodend
       method public void onButtonPush(BBjButtonPushEvent event!)
           a = msgbox("Button pushed! Text: " + #input!.getText(), 0, "Event")
       methodend
       method public void onTextChange(BBjEditModifyEvent event!)
           print "Text changed to: " + event!.getText()
       methodend
       method public void onClose(BBjCloseEvent event!)
           release
       methodend
   classend
   app! = new MyApp()
   app!.run()
   ```
   Explain why method-based is preferred: typed event parameter, encapsulation, no global state.

5. **process_events:** Explain in detail. `process_events` blocks execution until an event occurs, dispatches it to the registered callback, then blocks again waiting for the next event. It is an infinite loop that only ends when the program calls `release` or encounters an unhandled error. Must come AFTER all window/control/callback setup.

   **Gotcha box (:::caution):** `process_events` must be the LAST thing in your setup code. If you place it before adding controls or registering callbacks, the window appears briefly and the program may hang or behave unexpectedly. Pattern: create window -> add controls -> register callbacks -> process_events.

   Optional: `process_events,TIM=int` sets a timeout in seconds. If no event occurs within the timeout, execution continues past process_events. Useful for polling patterns, but most programs use the standard blocking form.

6. **release:** Explain that `release` terminates the program and closes all windows. This is the standard way to exit a BBj GUI program. Always register an ON_CLOSE handler that calls `release` so the user can close the window.

Cross-link to [OOP chapter](/object-oriented) for class syntax used in method-based callbacks.

Legacy callout (`<details><summary>`): "Reading Legacy Code: Label-Based vs Method-Based"
- Label-based callbacks (`setCallback(event, "label")`) are still valid but older-style
- You will see them in procedural BBj programs that predate Custom Objects
- Method-based callbacks are preferred in modern code for encapsulation and typed event parameters
- Both forms work identically at runtime -- the difference is code organization

**File 3: `docs/10-event-handling/02-events.md`**

Frontmatter: `sidebar_position: 2`, `title: "Event Types and Objects"`

Content sections:
1. **Opening (2-3 sentences):** Every BBj event has a constant (like ON_BUTTON_PUSH) and a corresponding event object (like BBjButtonPushEvent) that carries information about what happened. Knowing which events are available on which controls -- and what data the event object provides -- is key to building interactive applications.

2. **Core Event Types Table:** Present the most common events:

| Event Constant | Event Object | Fires On | When |
|----------------|-------------|----------|------|
| ON_BUTTON_PUSH | BBjButtonPushEvent | BBjButton | Button clicked |
| ON_CLOSE | BBjCloseEvent | BBjWindow | Window close requested |
| ON_EDIT_MODIFY | BBjEditModifyEvent | BBjInputE, BBjEditBox | Text content changes |
| ON_GAINED_FOCUS | BBjGainedFocusEvent | Most controls | Control receives focus |
| ON_LOST_FOCUS | BBjLostFocusEvent | Most controls | Control loses focus |
| ON_LIST_SELECT | BBjListSelectEvent | BBjListButton, BBjListBox | Item selected from list |
| ON_CHECK_ON | BBjCheckOnEvent | BBjCheckBox | Checkbox checked |
| ON_CHECK_OFF | BBjCheckOffEvent | BBjCheckBox | Checkbox unchecked |

   Note that each control type has a specific set of events it supports. The event constants are accessed as properties on the control object (e.g., `button!.ON_BUTTON_PUSH`).

3. **Event Objects:** Explain that event objects carry context about the event. All event objects extend BBjEvent and provide `getControl()` to get the source control. Specific events add their own methods:
   - `BBjEditModifyEvent`: `getText()` returns the current text
   - `BBjListSelectEvent`: `getSelectedItem()` returns the selected item text
   - `BBjButtonPushEvent`: minimal -- the event itself is the information

   Show an example using getControl() to identify which control fired:
   ```bbj
   method public void onFocus(BBjGainedFocusEvent event!)
       ctrl! = event!.getControl()
       print "Focus gained by control: " + str(ctrl!.getID())
   methodend
   ```

4. **Common Patterns:**

   **Multiple buttons, one handler:** Register several buttons to the same callback, use `event!.getControl().getID()` to distinguish:
   ```bbj
   #saveBtn!.setCallback(#saveBtn!.ON_BUTTON_PUSH, #this!, "onButton")
   #cancelBtn!.setCallback(#cancelBtn!.ON_BUTTON_PUSH, #this!, "onButton")

   method public void onButton(BBjButtonPushEvent event!)
       id = event!.getControl().getID()
       if id = SAVE_ID then gosub doSave
       if id = CANCEL_ID then gosub doCancel
   methodend
   ```

   **Live validation on text change:** Use ON_EDIT_MODIFY for real-time input validation:
   ```bbj
   method public void onTextChange(BBjEditModifyEvent event!)
       text$ = event!.getText()
       if len(text$) < 3 then #statusLabel!.setText("Too short")
       if len(text$) >= 3 then #statusLabel!.setText("OK")
   methodend
   ```

5. **Gotcha box (:::caution):** "Event handler method parameter type must match the event type. If you register ON_BUTTON_PUSH but your method signature takes `BBjEditModifyEvent`, you will get Error 208 at runtime. Always match: ON_BUTTON_PUSH -> BBjButtonPushEvent, ON_CLOSE -> BBjCloseEvent, etc."

Legacy callout: "Reading Legacy Code: Numeric Event Constants"
- Older code may use numeric constants instead of named properties: `CALLBACK(1, ...)` instead of `ON_BUTTON_PUSH`
- The named constants (like `ctrl!.ON_BUTTON_PUSH`) are preferred for readability
- Both refer to the same underlying event type numbers

**File 4: `docs/10-event-handling/03-legacy.md`**

Frontmatter: `sidebar_position: 3`, `title: "Legacy Event Patterns"`

Content sections:
1. **Opening (2-3 sentences):** Before setCallback, BBj and its predecessors used different event handling approaches. Understanding these patterns helps you read and maintain existing codebases. You should not write new code using these patterns -- they are here for reference only.

2. **CALLBACK Verb (Procedural BBj):** The CALLBACK verb is a procedural alternative to setCallback that predates Custom Objects. Syntax: `CALLBACK(eventType, subroutineName, contextID {, controlID})`. The handler is a label that GOSUBs and must RETURN. Show a brief example:
   ```bbj
   rem CALLBACK verb example (procedural style)
   sysgui = unt
   open(sysgui)"X0"
   print(sysgui)'window'(10, 10, 400, 200, "CALLBACK Example", $00100083$)
   print(sysgui)'button'(201, 50, 50, 100, 30, "Click")
   callback(ON_BUTTON_PUSH, onPush, sysgui, 201)
   callback(ON_CLOSE, onClose, sysgui)
   process_events
   onPush:
       a = msgbox("Clicked via CALLBACK verb", 0, "Event")
   return
   onClose:
       release
   return
   ```
   Explain key differences from setCallback: uses verb syntax not method call, references the SYSGUI channel number instead of control objects, requires numeric event type constants.

3. **READ RECORD Loop (Visual PRO/5 Era):** The oldest pattern, predating both CALLBACK and setCallback. The program polls for events in a loop using READ RECORD on the SYSGUI channel. Show a conceptual example (brief, not a full working program):
   ```bbj
   rem READ RECORD polling loop (Visual PRO/5 style)
   rem This is the oldest event pattern -- do NOT use in new code
   rem Shown here so you can recognize it in legacy codebases
   rem
   rem loop:
   rem     read record(sysgui, siz=6)event$
   rem     rem parse event$ to determine what happened
   rem     rem dispatch to handler based on event type
   rem     goto loop
   ```
   Explain in 2-3 sentences: READ RECORD blocks until an event arrives, returns raw event data as a string that the program must parse manually. This was the only option in Visual PRO/5 and early BBj. If you encounter this pattern, it is a strong candidate for modernization.

4. **Migration Path:** Brief note (3-4 sentences) on modernizing legacy event code. The progression is: READ RECORD -> CALLBACK verb -> setCallback. Each generation coexists -- you can mix them in the same program if needed during gradual migration. New code should always use setCallback with Custom Objects.

5. **Pitfalls box (:::caution):** "Do not mix READ RECORD and PROCESS_EVENTS in the same program. READ RECORD consumes events from the queue, which empties it before PROCESS_EVENTS can dispatch them. Choose one approach per program."

Legacy callout: "Reading Legacy Code: Recognizing Event Generations"
- **READ RECORD on SYSGUI channel:** Oldest pattern. Look for `read record(sysgui` or `read(sysgui`. Always a loop.
- **CALLBACK verb:** Middle generation. Look for `CALLBACK(ON_` at the verb level (not a method call).
- **setCallback method:** Modern. Look for `ctrl!.setCallback(` as a method call on a control object.
